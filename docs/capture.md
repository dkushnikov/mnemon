# The capture layer — what a URL capture does and how to read it

Phase 1 of the capture contracts made the gateway honest about *what* it published (three artifacts, three hashes, a receipt per capture — [`specs/2026-10-15-capture-contracts.md`](specs/2026-10-15-capture-contracts.md)). The capture layer, phase 2 ([`specs/2026-10-15-capture-layer.md`](specs/2026-10-15-capture-layer.md)), is about *whether what it published is the page*: one network policy for every request the engine makes, a fetch chain that knows when a page needs rendering, three converters checked against the saved page, a sanitizer, site capture from a reviewable plan, resolvers for arXiv and YouTube, a canonical identity for URLs, deadlines with named owners, chunked extraction under one budget, and an `index.md` whose rows are regenerated from the files behind a preservation step. Texts and plain-text files are §17; images and screenshots, read by a model and witnessed by tesseract, are §18. This page is the operator's guide to it; the spec is the contract.

The phase-1 facts hold unchanged: the gateway acquires and publishes, the model only extracts; `source.md` is immutable and its body is the capture-text byte for byte; `RESULT:` lines and exit codes come from the files; every write happens under the vault lock.

## 1. The fetch chain and what `egress` means

A URL capture (`mnemon add --url …`) acquires the page in up to three stages, in this order, and records every stage it tried in the receipt (`capture_report.fetch.stages`):

1. **direct** — the engine's own HTTP GET under the network policy: `http`/`https` only, no user-info, every address of every hop checked (private, loopback, link-local, reserved and every other address that is not globally reachable — a tailnet's or a carrier NAT's shared space included — are refused as `ssrf-blocked` / `ssrf-redirect`; an address of the NAT64 well-known prefix `64:ff9b::/96`, which a DNS64 network answers for a host without native IPv6, is judged by the IPv4 address it carries, so the policy lets a public host through there and still refuses a private one) and the connection pinned to the checked address, at most 5 redirects (each re-checked), a byte cap (`fetch_max_bytes`, 20 MB, decoded bytes, decompression bounded per chunk), connect/read timeouts (`fetch_timeout`) under the absolute acquisition deadline (the body is read one receive at a time, and a watchdog armed at the deadline shuts the socket down, so a server trickling bytes — in the body, or one header byte at a time before any body — cannot outlast it), one User-Agent (`fetch_user_agent`), **no cookies, no credentials, no proxies**. The response is classified (§2) and the chain stops, escalates or fails from that.
2. **rendered** — headless Chrome (`render-url.sh --html`) when the direct result is a JavaScript shell, a bot wall, a 403, or thin (fewer than `thin_words` visible words), or on `--render`. The raw of a rendered page is its post-JavaScript DOM HTML (`raw_kind: rendered`); it has no HTTP status and no final URL, and both are recorded as `null` rather than invented. Chrome runs with a throw-away profile and a mock keychain, a virtual-time budget, `render_timeout` and an output cap (`render_max_bytes`). **The policy does not police the browser**: its own connection, redirects, sub-resources and script-initiated requests are the browser's. The URL is checked before Chrome launches; that is a pre-validation of the name, not first-hop enforcement. `--no-render` skips this stage (and, because it means "no rendering", the external stage too). Without Chrome, a page that needed rendering fails as `environment` (exit 3) unless an external fetcher is allowed.
3. **external** — Firecrawl, then Jina Reader (`external_fetchers`), **only** when the instance says `external_fetch: auto` (the default is `off`), only for a JavaScript shell, a bot wall or a 403 after direct and rendered both failed, only for a URL that passes the policy, with keys from the environment (`FIRECRAWL_API_KEY`, `JINA_API_KEY`). A fetcher without a key is skipped with a note. A vendor's answer is classified like any other: a relayed wall is not a raw. `--no-external` skips the stage for one capture.

**`egress`** is where the request for the page physically went: `direct` (the engine or its browser, from this machine) or `external` (a vendor fetched the page on the engine's behalf). It is written into `source.md` only when it is `external` (`capture.egress: external`), and `mnemon doctor`'s `egress` line shows the instance's setting and whether each fetcher's key variable is set — never the key.

**Nothing in the chain is a way past a login, a paywall or a rate limit.** A login wall fails the capture (permanent, `blocked`/`login`); a paywall teaser with real text is published as `completeness: blocked` with the text before the wall; a 429 or a `Retry-After` fails as retryable and is retried later by the inbox's own backoff, never by the chain. One exception is a challenge page that *answers* with a 429 — the Vercel Security Checkpoint does, and names itself in the body: a 429 that carries a bot-wall marker is classified `bot-wall`, not `rate-limit`, and escalates once to the renderer (headless Chrome passes the checkpoint), then to an external fetcher when the instance allows it. When every stage ends on a wall the capture fails with `error_class: blocked`.

The same policy serves the site mapper and bundle fetcher, the depth helpers (`--depth`), the arXiv metadata request and URL PDF / audio downloads (`capture-fetch.py --expect pdf|audio`; `curl` is gone). The media tools (`yt-dlp`, the transcript library, `whisper`) are the second named boundary: the video URL's host is checked before they run; their own requests are theirs, under `transcribe_timeout`.

## 2. Completeness outcomes and how to read the `capture:` block

Two checks, both **diagnostics** — neither refuses a capture on its own:

**Acquisition** names what the fetched raw is, from one ordered decision table over the status, the headers and the visible words: `ok`, `thin`, `js-shell`, `bot-wall`, `forbidden`, `login`, `paywall`, `rate-limit`, `not-found`, `server-error`, `unavailable`. The chain decides from it (§1). The outcome is recorded as `capture.acquisition`, so "complete" never claims the fetch got the intended page — only that the conversion kept what the fetch got. The classification is one linear pass over at most the first 1 MB of the body (`CLASSIFY_MAX_BYTES`): the visible words, the markers and the JavaScript-shell signals all come from that prefix, and an unclosed `<script>`, `<style>` or `<title>` costs no more than a closed one (it swallows the rest, as in a browser) — a hostile page cannot hold the acquisition, and with it the vault lock, in CPU time that no deadline can interrupt. The conversion check is linear too: every regex over candidate markdown uses bounded, nesting-free character classes, so a page of 100 000 `[` or `(` converts in seconds, and whatever is not linear runs in a worker the supervisor kills at `convert_timeout` (§8).

**Conversion** compares the published text with a *reference* projected from the same raw bytes: the DOM text of the page's content subtree (`<article class="ltx_document">` for arXiv, else `<body>` without scripts, styles, navigation, footers, forms, cookie banners and reader comments). Three candidates are tried in order — `defuddle` (skipped for rendered, site and external raws), `pandoc`, the DOM text itself — each sanitized first (§3). A candidate wins when it contains every *eligible* reference line (6 or more words, or 20 or more characters of a script written without spaces, not a chrome line — the 2026-09-22 recipe's phrases of cookie banners, copyright lines and Substack's own footer and promos, in lines of at most 12 words — not the title) **with its word boundaries** — a line whose characters are all present but whose whitespace-separated words were glued together ("Deploythecompanybrain") counts as missing, while a word the page itself splits across inline markup (a drop cap, a link inside a word) is accepted in either form — and every h1–h3 heading. Otherwise the DOM text is published (`converter: dom-text`) with the page's own word boundaries, which satisfies the reference by construction while the inventory says what was lost. The DOM text is the fallback of last resort, never a failure: should it fail the check itself (a check defect), it is still published, as `partial` with the counts and `missing_examples` of its own check and the candidate note `dom-text failed its own check`; a conversion fails (`convert`, "no candidate produced text") only when the page holds no text at all, and the report then records every candidate that was tried. Reader-comment sections are cut only where a real widget is identified: a container id or class such as `comments`, `comment-list` or `disqus_thread`, or a heading like `12 Comments`, `Comments (3)`, `Leave a comment`; a section named *Discussion*, *Responses* or plain *Comments* is body text and stays.

Two things the diagnostics record without acting on them: `bytes_per_word` is flagged as `bloat` above 40 bytes, and because it counts whitespace-separated words a CJK page is always flagged — recorded only, never acted on. A page that came back `thin`, whose render was unavailable or failed, and that holds no text at all is kept as the acquisition says (A7) and then fails at conversion as `convert` (no text to publish), not as an acquisition failure.

`capture.completeness` is defined **relative to the saved snapshot**:

| Outcome | Meaning |
|---|---|
| `complete` | every eligible reference line is present with its word boundaries, every heading is present, no table or code block of the page is missing from the text |
| `partial` | something was lost — `missing_lines`, `glued_lines`, `headings_missing` and the inventory say what |
| `blocked` | a paywall teaser was published: the real text before the wall, nothing behind it (`blocked_kind: paywall`) |
| `unknown` | nothing to check against: plain text, PDFs, media transcripts of the engine's own media path, legacy rendered text, a page with no eligible line, and composites captured before phase 2 (a caption raw of the browser lane *is* checked, §7) |

The `capture:` block of `source.md` (additive to phase 1):

```yaml
capture:
  method: "direct+pandoc"        # <fetch>+<converter>: direct | render | firecrawl | jina | site + defuddle | pandoc | dom-text | text | mixed; captions:<lang>:<manual|auto> for a caption raw
  fetch: direct                  # the stage that produced the raw; `browser` = the browser lane's bundle (§7)
  converter: pandoc              # vtt-text for a caption raw
  acquisition: ok                # the classification of the fetched raw (§2)
  completeness: complete         # complete | partial | blocked | unknown
  reference_lines: 212           # lines of the reference, eligible lines, and what the chosen candidate lacked
  eligible_lines: 96
  missing_lines: 0
  glued_lines: 0
  headings_missing: 0
  repairs: "svg_icons=4,next_images=2"   # the sanitizer's counted repairs, or none
  canonical_version: 2
  http_status: 200               # null for a rendered page
  egress: external               # only when a vendor fetched the page
  blocked_kind: paywall          # only when completeness is blocked
  fidelity: converted            # phase 1: exact | converted | transcribed
  raw_kind: response             # response | rendered | composite | transcript | captions | file | site
  raw_sha256: "…"
  text_sha256: "…"
```

`RESULT:completeness=`, `RESULT:acquisition=` and `RESULT:canonical_url=` are printed by `mnemon add`; the full fetch and conversion reports live in the receipt (`capture_report.fetch`, `capture_report.text`), and when `archive_dir` is set the final report is frozen next to the raw as `<revision>.report.json`. `missing_examples` in the conversion report shows up to five of the lines that were lost.

How to read a capture, in practice: a `partial` source with `missing_lines: 1` and `headings_missing: 0` is usually a caption or a footnote; a `partial` with `converter: dom-text` and `tables` lost in the inventory is a page whose tables did not survive conversion — the raw is retained, so a better converter later can redo it without a fetch (`mnemon add --resume` after a reconversion-capable release). `thin` under `acquisition` means the page had fewer than `thin_words` visible words even after rendering was tried: a landing page, a stub, or a site that serves its content elsewhere — consider `--site` or `--depth auto`.

## 3. Sanitation

The sanitizer runs **before** the check, counts every repair, and never guesses a position. At the HTML level: every `<math>` element becomes the text of its TeX source — `$\theta$`, display math as `$$…$$` (LaTeXML writes both the glyphs and the source, so the DOM text used to read `θ\theta` while pandoc wrote `$\theta$`, every formula line counted as missing and a paper fell back to the DOM text without its tables); an SVG with text becomes a paragraph of its labels and an icon SVG is removed; LaTeXML listing lines become fenced code; `[⬇](data:…)` download buttons go (a `data:` link that carries real text is unwrapped to its text, never dropped); merged-cell tables are rewritten into simple tables (cells duplicated across their span, stacked header rows joined with " · ") so pandoc never emits `[TABLE]` for them — spans are clamped to 1 000 and a table whose expansion would exceed 20 000 cells is left as it is and counted `tables_unrepaired`, with the conversion deadline (`convert_timeout`) checked between tables. At the markdown level, fence-aware (nothing inside a code fence is touched): inline `data:` images become `*[inline figure omitted at capture: alt]*`, remaining `data:` links are dropped, Next.js image URLs become `*[img: alt]*`, LaTeXML residue (`\iow_now:Ne`, macro residue before the title) is removed, blank-line runs collapse. Both levels are idempotent. `bytes_per_word` is recorded and flagged above 40, never acted on.

`published:` is the gateway's decision from the converter's dated candidates: for `source_type: paper` the arXiv `citation_date`; for `article` an `article:published_time` or the `datePublished` of an Article / BlogPosting / NewsArticle / ScholarlyArticle JSON-LD node — never a WebSite or Organization node, never for a site capture, and omitted when more than one distinct date is found (the candidates are kept in the receipt).

## 4. Canonical identity

The literal URL stays in `url:`. Every new URL capture also writes `canonical_url:` — the computed identity under the current rule set, version 2 (`capture.canonical_version: 2`; v1 stays callable, and a receipt recorded under v1 replays under v1) — and the folder's `resource_sha256` is derived from it. The rules are conservative: whitespace trimmed; scheme and host lowercased; the default port dropped; percent-encoding normalized in the path; tracking parameters removed from the query (`utm_*`, `fbclid`, `gclid`, `msclkid`, `mc_cid`, `_hsenc`, `ref_src`, `hide_intro_popup` and the rest of the list in the spec) while every other parameter is kept in order; the fragment dropped unless it is an application route (`#/page-a`, `#!…`); arXiv and YouTube resolved to one form per paper or video; and, in version 2 (2026-10-28), two host-scoped share parameters — X's `?s=` / `&t=` on `x.com` and `twitter.com`, Substack's `?r=` / `showWelcomeOnShare` on `*.substack.com` and on the apex reader app's post links — dropped on those hosts only (the same post shared by two people is one resource there; a folder captured under v1 with a share-tagged URL is found by a v2 request of the same post — the lookup compares under the current rules — and `mnemon audit --canonical` groups such pairs). **Not** done, on purpose: `www.` stripping, `http` → `https`, trailing-slash collapsing, lowercasing paths, following redirects (the redirect target is recorded as `final_url`, an alias for lookups, never the identity).

Consequences: two `add` calls with `?utm_source=a` and `?utm_source=b` are one resource (the second answers `skipped-duplicate` and reports the canonical URL); `?s=alpha` and `?s=beta` are two pages on any host but X, where `s` is the share tag. Lookups find every folder — new or phase-1 — whose URLs canonicalize to the same string and choose the head deterministically (the folder not superseded by another, latest capture date first); a phase-1 folder found this way resumes or dedups exactly as before, and its receipt replays under its own schema (`mnemon-request/1`), never re-derived. Two consequences of that binding (A4): a `/1` receipt binds the literal `url`, so replaying it with another literal `utm` variant of the same page exits 2 (binding mismatch) — a new capture of that variant answers `skipped-duplicate` instead; and a `/1` request knows none of the new flags, so a `/1` replay given a non-default new flag such as `--no-external` exits 2 as well. A `/2` receipt binds the literal `url` just the same: replaying it (`--capture-id`) with another `utm` variant of the same page is a different request — exit 2, `capture-id reuse with a different request` — while a new capture of that variant, without the id, answers `skipped-duplicate` under the canonical identity. The page's own `<link rel=canonical>`, which the depth probe used to write into `canonical_url`, now lives in `declared_canonical_url`.

`mnemon audit --canonical` groups the vault's folders by the current canonical form of their URLs (v2) and prints the groups of two or more with their revisions, `supersedes` links and extract status. It writes nothing and merges nothing — a duplicate from before canonicalization is yours to resolve (`mnemon add --recapture` on the one you keep; `mnemon add --recapture --supersedes <rev>,<rev>…` to supersede the whole group with one re-capture; or leave both). It reads each `source.md` header through its closing `---` or `...` within 256 KB, the one rule the lookup and the reindexer share.

**Depth folding** (`--depth auto`, the default for a thin landing) runs after the landing was acquired through the chain, on the staged raw, under the remaining acquisition budget — the probe has no cap of its own — and never on a landing the chain classified as a paywall teaser (nothing deeper is fetched behind a wall). A folded capture is published as a composite (`raw_kind: composite`): the converted landing followed by the folded targets, retained as `<revision>.txt`. **A depth composite keeps the composite text only** — the landing's HTML is not retained beside it, so a composite cannot be reconverted from HTML the way a plain page can (`mnemon add --resume` reuses the retained text as it is); its completeness covers the landing part only and says so. Retaining the landing HTML next to the composite is a phase-3 follow-up. The fold's manifest is YAML, so the helper needs PyYAML; on a python without it the fold is skipped — the landing is captured alone, one stderr line says `depth fold skipped: PyYAML is missing`, and the receipt records `depth: skipped (no PyYAML)`.

## 5. Site capture with a reviewable plan

A site is many pages; the capture contract wants one resource per entity. Site capture makes the **landing** the resource and the plan its input:

```bash
mnemon site map https://example.com/ --out plan.json          # discover pages, write the plan (nothing captured)
# review or edit plan.json: flip include flags, add a host, drop a role
mnemon add --url https://example.com/ --site plan.json         # capture the included pages into one bundle
mnemon add --url https://example.com/ --site auto              # map and capture in one run (the plan is kept with the receipt)
```

`site map` discovers same-site pages from the landing's links (after rendering when the landing is a JavaScript shell), `/sitemap.xml` and the sitemaps named in `/robots.txt` — a sitemap index is followed two levels deep (`sitemap_index.xml` → `help/sitemap.xml` → `help/<product>/sitemap.xml`), at most 25 sitemaps and 20 000 URLs per map, the sub-sitemaps under the landing's section first — `/llms.txt`, documentation tables of contents and a linked GitHub README (its text only). Same-site means the landing's host (with or without `www.`), its `docs.` / `help.` / `developer(s).` / `blog.` / `api.` / `learn.` / `support.` subdomains, or a host the plan lists explicitly. Every page gets a **role** (`landing`, `product`, `docs`, `llms_txt`, `blog`, `pricing`, `careers`, `job`, `github_readme`, `legal`, `localized`, `howto`, `other`), an include/exclude decision and a reason: legal, localized, how-to and other pages are excluded by default (`en` and `en-*` paths or hosts are never `localized` — an English docs tree under `/en/` is the site's content — and neither is the landing's own locale prefix, read from its final URL as well). When the landing is not the site root, `product` is scoped to the landing's first path segment: a same-site page outside it (`/store/` for a landing `/air/`, `/products/…` for a docs landing under `/help/`) is `other` unless it is a docs, blog, pricing, careers or job page. `--include` / `--exclude` regexes are searched in the URL's **path plus `?query`** (never the scheme or host), so an anchored `^/blog/` or `^/help/air/` does what it says: `--include` **restricts** the plan to the landing and the pages matching some include regex (a matching page the rules excluded by role is re-admitted), `--exclude` then removes, and the cap `site_max_pages` (40) applies last, keeping the pages under the landing's section (its URL's directory — `/help/air/` for a docs page, `/air/` for a product landing; docs-TOC pages count as in it) first, then by role priority, then in discovery order. `robots.txt` is honoured as RFC 9309 defines it — the rules of **each origin** a page belongs to (`docs.example.com` has its own `robots.txt`, fetched the first time a page or a redirect hop lands there), matched against the path *and* the query, product token `mnemon` else `*`, longest match — a plan cannot include a disallowed page; an unreachable `robots.txt` disallows everything on that origin, a 4xx allows everything; the mapper keeps at least one second between requests to one host and stages its own work in a private temporary directory. `--no-render` and `--no-external` given to `mnemon add --site auto` govern the mapping of the plan as well as the bundle, and the mapper receives the instance's external-fetch settings exactly as the bundle fetcher does — a landing that needs a vendor fetch is mapped through the same chain it will be captured with.

`mnemon add --site` revalidates the plan (its landing must equal `--url`, the included pages must fit the cap, no robots-disallowed page) and fetches every included page through the chain of §1 — the landing first (a landing that fails is fatal), every other failure recorded and skipped — into a **bundle** `<revision>.site/` whose manifest names every member with its size and hash (`raw_sha256` is the manifest's hash). Each page carries a **disposition** that stays visible in the manifest, the report and `folded_sources:` of `source.md`: `captured`, `fetch-failed`, `skipped-timeout` (the `site_timeout` ran out) for acquisition; `converted`, `convert-failed` for conversion. The body is a composite — `# <landing title> — site capture`, then `## Part n — <url> (<role>)` per converted page in plan order — and:

```yaml
site_pages: "7/8"              # converted / included
folded_sources:
  - url: https://example.com/product
    role: product
    disposition: converted
    converter: pandoc
    completeness: complete
    missing_lines: 0
  - url: https://docs.example.com/guide
    role: docs
    disposition: fetch-failed
capture:
  raw_kind: site
  completeness: partial          # complete when every included page converted and every judged page is complete
  method: "site+mixed"           # or site+<converter> when one converter served every part
```

The aggregate `completeness` is `complete` when every included page converted and every converted page that has a reference is `complete`; parts without a reference — the README, `llms.txt`, a page with no eligible line — keep `completeness: unknown` in `folded_sources` and are neutral in the aggregate, so a site that includes a README can still be `complete`. `blocked` when the landing is a paywall teaser, `partial` otherwise.

A landing with an existing revision needs `--recapture` for a site capture (the new revision `supersedes` the plain one); `--recapture` on a partial site capture fills the omitted pages; `--resume` only finishes the extraction from the retained bundle. A bundle is verified like a file (every member's hash against the manifest) before every reconversion; a modified or missing member after publication is `evidence-mismatch`. `--dry-run --site plan.json` lists the pages and fetches nothing. The small report `capture-site.py fetch-bundle --report` writes (`mnemon-site-fetch/1`: the dispositions and the error fields) is not a frozen seam contract — the gateway reads only its error fields when the bundle fails; the manifest and the one stdout line are the contract.

## 6. arXiv

`arxiv.org/abs/<id>`, `/pdf/<id>`, `/html/<id>`, with or without `vN`, are one paper (`canonical_url: https://arxiv.org/abs/<id>`), `source_type` defaults to `paper`, and the content is the **full text**, never the abstract page: the fetch resolves the version once from the abstract page of the requested version (or the latest) — `citation_*` metadata (authors, `published:`), the version number — and fetches that version's HTML (`html/<id>vN`), else its PDF through the `pdf` row. `arxiv_version` (fetched) and `arxiv_requested_version` are written to `source.md`. An explicit `v1` in the URL archives v1, not v3; a later version is a `--recapture` with `supersedes`; asking for another version of a captured paper without `--recapture` answers `skipped-duplicate` naming the captured version. Conversion keeps `<article class="ltx_document">` and applies the LaTeXML sanitation (listings, download buttons, merged tables, residue).

## 7. YouTube

Captions are chosen **by the video's language**, read from `yt-dlp`: a manual track in that language · an automatic track in it (YouTube's `-orig` track first) · a manual `en` or `ru` track · an automatic `en` or `ru` track · the first manual · the first automatic · `whisper`. A Portuguese video with Portuguese captions is no longer captured from machine English. `source.md` records `transcript_language` (the track's language) and `original_language` (the video's), `capture.method` is `captions:<lang>:<manual|auto>` or `whisper:<model>`, and `media.json` under the attempt directory carries `language`, `original_language`, `track`, `channel` beside the phase-1 keys. The receipt's `media_meta` is recorded at acquisition and is authoritative on a replay: a resumed youtube-whisper capture that re-transcribes the retained audio takes `video_title`, `upload_date`, `duration` and `video_id` from the receipt, not from a filename. `embed/`, `live/`, `shorts/`, `youtu.be` and `music.youtube.com` forms all resolve to the same video; an explicit `--origin url` on a YouTube URL captures it as a page instead.

**Walls.** YouTube answers a host it distrusts with a bot wall — `yt-dlp` prints `Sign in to confirm you’re not a bot`, the transcript library `YouTube is blocking requests from your IP` — and the engine does not try to pass it (no cookies, no proxies: the browser lane below is the designed route around walls). Such a capture fails as `error_class: blocked`, `RESULT:acquisition=bot-wall` (a 429 is `rate-limit`), `retryable: false` (a retry in a minute meets the same wall; a rate limit is retryable), with the tool's own line in the receipt's `error` and `runs/<id>/attempt-N/error.json` (`mnemon-media-error/1`: `error_class`, `kind`, `stage`, `error`, `retryable`) — and `raw_path` null, since no raw was staged. Any other failure of the media helper carries its cause in the receipt's `error` the same way. The chain still stops at the metadata step today; letting a metadata failure degrade and continuing to captions is the open part of the media issue.

**The browser lane** (capture layer A13; GH #12, #26). A video the engine's media path cannot reach is captured through the reader's own browser session, by a producer that runs *outside* the fetch chain:

```bash
mnemon browser-lane youtube <url> [<url>…] [--browser safari] [--context <ctx>] [--intent <text>] [--session <name>] [--recapture]
mnemon browser-lane youtube <url> --no-add            # the bundle only; prints the mnemon add argv to run later
mnemon add --url <url> --media-bundle <dir>           # what the producer runs for each bundle
```

`browser-lane youtube` takes the videos **one at a time, in order**: one `yt-dlp --cookies-from-browser <browser> --dump-single-json` for the metadata and the caption listing, one caption download of **exactly one track** chosen by the rule above (manual before automatic, the video's language first, YouTube's `-orig` track first; several tracks in a row answer HTTP 429), a pause between videos (`--pause`, 2 s). Each video gets a **bundle** under `$XDG_STATE_HOME/mnemon/browser-lane/<video_id>/<timestamp>/`: `media.json` (`mnemon-media/1` — the same flat record `media-extract.py` writes — plus `chapters`, `captions_path`, `captions_code` and a `producer` block naming the lane, the browser and yt-dlp's version) and the track as yt-dlp wrote it (`<video_id>.<code>.vtt`). The producer then runs `mnemon add --url <video> --media-bundle <dir> --import-source browser-lane --producer-fidelity exact|model-transcribed` (a manual track is the publisher's text, an automatic one is YouTube's model) through the dispatcher that started it, with the instance resolved once. A wall yt-dlp meets even with cookies is reported as `blocked` for that video and the lane moves on to the next; the last line is a summary (`browser-lane: N video(s) · captured N · blocked N … — not captured: <id> (bot-wall), …`, `--json` for machines) that names every video not captured with its reason. The video's directory is made before the first yt-dlp call (capture layer A18): an attempt that ends blocked, failed or past `--timeout` keeps `error.json` (`mnemon-media-error/1`: class, stage, wall kind, the line, retryable) and `stderr.txt` (yt-dlp's `ERROR:`/`WARNING:` lines only, paths and session values redacted) there, without `media.json`, and its line ends with ` · diagnostics: <dir>`; the printed cause is the line the wall classifier matched, else yt-dlp's first `ERROR:` line. **Cookies never reach the engine**: yt-dlp reads the browser's store for its own requests and writes nothing of it; the bundle holds the record and the track, nothing else; the only thing that reaches a log is the browser's name. Safari needs nothing further; Chrome asks for its keychain item on screen the first time and the lane neither suppresses nor answers that prompt.

`mnemon add --url <youtube url> --media-bundle <dir>` is the gateway's door for such a bundle: it validates it before anything is written (a `mnemon-media/1` record, `captions_path` a plain file name inside the directory, the record's `video_id` equal to the URL's — the dry-run refuses the same things), **never runs a media tool and never enters the fetch chain**. The track is the raw (`<revision>.vtt` in the archive, `raw_kind: captions`, its hash bound in the request as `input_sha256` — a replay with another bundle is another request, exit 2), and `capture-captions.py` converts it: the cues, YouTube's rolling repeats and re-displays removed, paragraphs of speech, one `## <chapter title> (m:ss)` heading per chapter of the video, in order. The conversion is **checked against the raw it came from**, as a page is checked against its saved HTML: every caption line of three or more words must be present in the text as a token sequence, every chapter heading present → `completeness: complete`, else `partial` with the counts (`reference_lines`, `eligible_lines`, `missing_lines`, `headings_missing`). The `capture:` block says `fetch: browser`, `converter: vtt-text`, `method: captions:<lang>:<manual|auto>`, `fidelity: transcribed`, `producer_fidelity: <the producer's claim>`; the frontmatter carries `transcript_language`, `original_language`, `duration`, `upload_date`, `video_title`, `chapters: N`, the channel as `author`, `import_source: browser-lane`. `mnemon add --resume` and a replay after a crash reconvert the retained `.vtt` from the receipt's `media_meta` (which keeps the method and the chapters); the bundle is not needed once the raw is published. A video already in the vault (through the lane or otherwise) answers `skipped-duplicate`; `--recapture` makes a new revision that supersedes it — the way to replace a `--file-text` workaround with a captioned capture.

URL audio (`--origin audio --url …`) is downloaded through the policy and named by a content sniff (`.mp3`, `.m4a`, `.wav`, `.ogg`, `.flac`, `.aac`, `.mp4`, `.webm`), the URL's extension as the fallback.

## 8. Timeouts

Every deadline has one owner, children run in their own process group, budgets are passed down — so a hung download no longer holds the vault lock forever:

| Budget | Owner | What it bounds |
|---|---|---|
| `acquire_timeout` (300 s) | `capture-fetch.py` | the whole acquisition of one URL: direct, rendered and external stages together |
| `fetch_timeout` (60 s) | the policy | one direct request (connect = min(15, T/4), read = the rest); each page of a site |
| `render_timeout` (90 s) | the render stage | headless Chrome for one page |
| `site_timeout` (900 s) | `capture-site.py` | mapping; the bundle loop (pages left over are `skipped-timeout`, the bundle is published partial when the landing was captured) |
| `transcribe_timeout` (3600 s) | `media-extract.py` | yt-dlp, ffprobe, whisper and the caption fetch (its own subprocess, so a hung library call is killable) |
| `convert_timeout` (120 s) | `capture-text.py` | the whole conversion of one retained raw, in a worker process the supervisor kills past it (defuddle and pandoc under the same deadline inside it); a site bundle's assembly as a whole, each page with what is left |
| `extract_timeout` (900 s) | `extract-run.py` | one extractor call (phase 1) |

On expiry the owner kills its process groups (SIGTERM, a 2 s grace, SIGKILL), reaps them, writes `error_class: timeout` with the `stage` into its report and exits 124; the gateway records `FAIL_CLASS=timeout` with the stage. Two classes of timeout: an **acquisition** owner's (`capture-fetch.py`, `capture-site.py map` / `fetch-bundle`, `media-extract.py`) is retryable — a later run may get the page, and a timeout after the raw was published is resumed by reconverting the retained raw, never by refetching; a **conversion** timeout — a `capture-text.py` exit 124 is the class `timeout` with `stage: convert`, and so is an assembly whose landing the budget killed — is **not** retryable: a page that cannot be converted in the budget will not convert on a retry either, the raw stays published, and `mnemon add --resume` after raising `convert_timeout` is the way back. The gateway itself holds no outer timeout. `capture-text.py` is a thin supervisor: the whole conversion runs in a worker process (its own process group) that the supervisor kills at `convert_timeout`, so an in-process scan that never checks the deadline cannot hold the vault lock; inside the worker, when `defuddle` or `pandoc` outlives the remaining budget the tool is killed with its group and that **candidate is skipped** with a note (`pandoc timed out after N ms`), the next candidate is tried and the DOM text needs no tool. `capture-site.py assemble` converts every page of a bundle through the same worker with the remaining budget, and `map` / `fetch-bundle` run as workers under the CLI's own watchdog (`site_timeout` plus a 10 s teardown grace). Any other conversion failure is `convert` to the gateway, which honours the report's `retryable`: the converter walks the page's tree without recursion and caps its depth at 2 000 levels (deeper elements are flattened into the capped one), so 20 000 nested `<div>` or 6 000 never-closed table cells still convert; a document nested past what the interpreter can parse at all is `nesting` — permanent, never retried.

## 9. Chunked extraction

Capture-text above `extract_inline_max_bytes` (400,000 bytes) is no longer refused: it is split at heading boundaries outside code fences (else at blank lines) into at most `extract_max_parts` (8) parts of at most the inline limit, each part is extracted through the fenced extractor with the part template (`extract-part/1`: a title, a summary, standalone claims with a domain each, verbatim quotes — no rating, no body), and one merge run receives the parts' outputs instead of the content and returns the usual `extract/1`. `extract.md` records `extraction: chunked` and `parts: N`; the receipt records every call under an id that names the part, the round and the attempt (`part-3-r2-a1` is the validation re-run of part 3; `single-r1-a1`, `merge-r1-a1`), so a re-run is its own call, reconciled exactly once. **One budget for the capture's lifetime**: with `extract_max_usd` set, every call — parts, merge, validation retries, resumes — is debited from it, each call gets the remaining budget as its own cap, and a call that would start with nothing left stops the capture as `budget-exhausted` (retryable only with a raised budget); a call whose cost came back unknown keeps its reservation until `mnemon add --resume <id> --assume-cost <usd>` reconciles it. A phase-1 receipt that already spent `cost_usd` has that spend seeded as one reconciled `single` call before the ledger starts, so the budget keeps counting it. More parts than allowed, a single unsplittable span above the limit, or merge inputs above it → `unsupported-size`, as before. `--resume` re-runs every part (there is no part cache) and keeps debiting the same budget.

## 10. Index regeneration and `index_note`

`mnemon reindex` (also the post-extract hook of every `mnemon add`) **regenerates every row** of `index.md` from `Sources/*/extract.md` and `source.md` — a changed rating changes the row — instead of freezing a row forever once written. Three things are derived from the files (the first two used to be hand-edits):

- **`index_note`** — a one-line `index_note: "…"` in a folder's `extract.md` (extract.md is mutable; source.md is not) is appended to its row as ` — <note>`. Put a durable annotation there, not in `index.md`.
- **`supersedes`** — a re-capture's `source.md` names its predecessor (`supersedes: "<revision>"`, or `Sources/<revision>/extract`), or several predecessors as a YAML block list (`supersedes:` on its own line, then one `  - "<revision>"` line each) when `mnemon add --recapture --supersedes <rev>,<rev>…` (comma-separated, or the flag repeated; each revision must exist; written sorted, without repeats) resolves a group of duplicate legacy revisions of one resource in a single re-capture — one revision stays the scalar form, so every existing file and receipt reads as before. The reindexer marks each old row ` ⤳ superseded by [[Sources/<new>/extract|<title>]]` from that — one marker per successor, a successor without `extract.md` linked through its `source`, a cycle reported on stderr and not marked, a target that no longer exists counted as `Dangling-supersedes` and marking nothing. Nothing is written into any `source.md` or `extract.md`.
- **A video's title** — a row whose `source.md` carries `video_title:` (every YouTube capture: the engine's media path and the browser lane, §7) shows the video's title; the extractor's own `title:` stays in `extract.md` as its own field (the extract describes the talk, the catalog names it). The ` ⤳ superseded by […|<title>]` marker follows the same rule — one function names a folder for both, so a legacy `extract.md` without a `title:` now takes `source.md`'s `title:` before its `# ` heading, as the marker always did. `mnemon search` and `RESULT:title=` follow the same rule — the search result through the same function, the result line through the gateway's own reader — so a video is named by its title wherever the engine names it; the extractor's `title` stays in `extract.md`. `mnemon search` also **finds** a video by the words of that title without `--include-source`: the default scan reads each extract together with `video_title` from the header of its `source.md` — that field alone, never the transcript (a revision without an extract still needs `--include-source`). The first `mnemon reindex` after this change rewrites the rows of existing videos, and the hand-edit report below keeps the old ones.

**The hand-edit report.** Before a regeneration replaces an existing row with different text, the exact old row is appended under a dated heading to `<vault>/_inputs/index-hand-edits-<YYYY-MM-DD>.md` — every distinct old row, once (deduplicated by folder and the row's hash across the day's file, so a second edit on the same day is kept too), the file and its directory fsynced — and only then is `index.md` replaced (atomically). If that file cannot be written the index is left untouched and the run exits 1 with the reason. `mnemon reindex --no-hand-edit-report` skips the step explicitly. The first run after this change preserves every hand-written marker and annotation the old index carried; move what you want to keep into `index_note:`.

The counters line reports `Superseded=N` (and `Pending`, `Bookmarks`, `Legacy`, `Dangling-supersedes`, `Preserved`, `Malformed-frontmatter` when non-zero); the pending note in `index.md` names `mnemon add --resume <revision>` for sources captured without an extract, lists bookmark cards (`tier: bookmark`, §15) on their own line with the triage doors, and counts legacy placeholders (`status: bookmark`, `fetch_status: failed` in `source.md`, not resumable) apart. `mnemon status` reports `superseded` and `chunked` from the same scans.

## 11. Doctor and audit

`mnemon doctor` gains three observational lines: `capture-deps` (defuddle ≥ 0.6, pandoc ≥ 3, Chrome by the renderer's own candidate list — "rendering unavailable" without it — and Poppler, with versions; for images its two parts `ocr` and `image-reader`, §18; a missing tool warns, never fails), `egress` (the instance's `external_fetch`, and per fetcher whether its key variable is set — never the value), `canonical` (`canonicalization v2`; v1 receipts replay under v1). A fourth, `media-tools` (capture layer A18), follows `capture-deps`: yt-dlp's version and its age in days, the JavaScript runtimes yt-dlp itself reports it can use (`yt-dlp -v --ignore-config`; a `node` on PATH is not one — yt-dlp enables only `deno` by default) and its challenge solver; it warns past 90 days, on no runtime, on an unknown version, and on a missing yt-dlp, and never fails. `deps-python` no longer names `requests` (every request goes through the policy on the standard library; `pyyaml` stays for the depth manifest). `captures` also lists folders whose `source.md` header is not closed within 256 KB (`malformed-frontmatter`): the lookup cannot read them, and it says so rather than truncating silently. The `captures` line names one failed receipt for `--resume` and the door to all of them: `mnemon doctor --list captures` prints every receipt the check counts — failed and extract-failed first (`<capture_id>`, `<state/error_class>`, the revision or `-`, the error with its stage and whether it is retryable), then integrity errors, receipts whose revision files are gone, unreadable files (GH #15), and last the **resolved** ones: a failed receipt that published nothing, whose resource the vault now holds through another capture (the same `resource_sha256`, else the same canonical URL — a bot-walled video captured again through the browser lane, a `--file-text` capture with `--canonical-url`), is `failed/resolved`, named with the revision that holds the resource, and **not counted** as failed (no `--resume` hint for it; the summary notes `N failed receipt(s) resolved by a later capture …`). The doctor only observes: the receipt stays in the ledger as the record of the failed attempt. `mnemon audit --canonical` is §4; `mnemon audit text-mismatch`, the bodies of pre-contract captures against their raws, is §16.

## 13. What survives

With `archive_dir` set, what survives the loss of this machine's local state is in the archive: the raw (a file, or a bundle with its plan and per-page fetch reports), the frozen final report `<revision>.report.json`, and, in the vault, `source.md` with its frontmatter summary. The receipt — the ledger under `~/.local/state/mnemon/vaults/<id>/` — is local and re-derivable only for the facts those carry; a new machine captures afresh and finds the old folders through the canonical lookup.

An `archive_dir` inside a synced folder (iCloud Drive, or another File Provider folder on macOS) works, with one hazard the engine absorbs: the provider can rename a freshly published raw back to the staged name `.<revision>.<ext>.staging-<pid>` it saw while it uploaded the file. The engine publishes the raw from a fresh copy, so no long-lived staged name exists; a copy that the provider renamed back anyway is renamed into place by the next capture or replay (a `NOTE:` line, `raw_restored` in the receipt) and never swept as stale staging. The raw is verified before `source.md` names it and again before a capture reports a revision: a raw that is gone or changed after the source publication is `integrity-error` with `error_class` `raw-missing` or `raw-mismatch` (exit 1, the revision kept, nothing refetched); `mnemon doctor --data` names it under `store/archive` and `store/ledger`. A raw that was deleted before this rule is not recoverable by the engine ([capture contracts §15, A12](specs/2026-10-15-capture-contracts.md)).

## 15. Tiers — the bookmark card, promotion and triage

A capture has a **tier** (vault store §4): `full` — everything above — or `bookmark`, a cheap deterministic card for "I want this in the vault, not read yet". Scanners that bring in tabs, saved posts and forwarded links bookmark by default; a full extract is the reader's (or a collection rule's) explicit promotion. The tier is a stored fact of `source.md` (`tier: bookmark`; absent = full).

```bash
mnemon add --url https://example.com/post --tier bookmark --title "A post" --intent "saved from tabs"
mnemon triage list                      # the queue: current bookmarks, newest first
mnemon triage promote <revision>        # capture it in full — the new revision supersedes the card
mnemon triage dismiss <revision> --why "…"   # the judgement about the resource; restore reverses it
```

**The card.** `mnemon add --tier bookmark` fetches nothing and runs no model: `source.md` is published with `tier: bookmark`, its body the card — `# <title or url>`, a blank line, the URL, and the `--intent` when given (for a text on stdin or `--file-text`, the text itself) — and the usual identity (`canonical_url`, `resource_sha256`, a revision, a receipt in state `bookmarked`), `capture.method: bookmark`, `fidelity: exact`, `completeness: unknown`, no raw. There is no `extract.md`: `mnemon add` answers `RESULT:status=bookmarked`, `RESULT:extract=none`, `RESULT:tier=bookmark`, exit 0; the index notes the card under its own line (never as "captured without extract"), `mnemon search` finds it with `--include-source` as a `source` result with `tier: bookmark`, and the doctor's `data/stubs` leaves it alone. A bookmark takes a URL or a text: a file (PDF, audio, a document) is captured in full or not at all. `--resume` of a bookmark is a usage error — there is nothing to finish; promote it instead.

**Promotion — supersede, never overwrite.** A full `mnemon add` of a bookmarked resource is the promotion: no `--recapture` needed, the new revision `supersedes` the card (a NOTE says so), `promoted(rev)` becomes true for the card and it leaves the queue. A bookmark request for a resource the vault already holds — bookmarked, captured or extracted — is a `skipped-duplicate` (it never resumes anything); `--recapture --tier bookmark` refreshes a card (a changed title) but is refused when the head is a full capture: a bookmark never supersedes a full one. The request binds `tier` only when it is `bookmark`, so every receipt written before this release keeps its hash, and a promotion replayed under its capture-id without `--recapture` is the same request.

**The queue — `mnemon triage`.** `list` shows every current bookmark-tier revision (`tier: bookmark`, or the legacy placeholder `status: bookmark`) with a status derived from the files: `bookmarked`, `dismissed`, or — on `--status promoted|all` — `promoted` (a full descendant exists); `--status dismissed|all` also lists the dismissed **full** revisions, since the judgement is about the resource whatever its tier (the JSON row carries `tier`, the text status column reads `dismissed/full`; `counts.dismissed` counts the cards, `counts.dismissed_full` the rest). `dismiss <rev> [--why …]` stores the judgement **about the resource on its latest revision** — a card or a full capture (a superseded revision is refused naming the head; a full revision without extract.md is unfinished and refused — `mnemon add --resume` first): in `extract.md` as `status: dismissed` (+ `dismissed: <date>`, `dismissed_why`, and `dismissed_from` — the word the status had) when the revision has one, else in `Sources/<rev>/triage.md` — the one mutable file of a revision without an extract; `source.md` is never touched. `restore` reverses it (the prior word comes back as `status: <word>`, every other line as it was). A promotion supersedes the carrier, and the judgement lapses with it — a new revision invites a new judgement. The judgement is "not now", not "never": a bookmark request for a dismissed resource is a `skipped-duplicate` that says so — `RESULT:judgement=dismissed` — so a scanner can tell "already in the queue" from "dismissed" and never resurrects it; a full `mnemon add` of the resource is the explicit decision to read it and promotes. `promote <rev> [flags…]` runs `mnemon add` for the resource (a URL card by its URL, a text card by its own body; `--dry-run` prints the command). `dismiss` and `restore` run under the vault lock; `status --brief` adds ` · N bookmarks (k dismissed)` when the queue is not empty. (The content-aware URL-list triage spike, `mnemon triage <file>`, was retired on 2026-10-28; scoring of a URL queue returns as a phase-4 stage over this queue.)

**`--canonical-url` — identity by document, not by file.** A `--file`, `--file-text` or stdin capture may name the document its bytes came from: `mnemon add --file export.md --canonical-url "https://docs.google.com/document/d/<id>/edit"`. The resource is then that URL's canonical form (`resource_kind: url`, `canonical_url:` computed, the literal in `url:`, `origin` and `origin_path` unchanged) — a document exported twice is one resource: the second export answers `skipped-duplicate`, `--recapture` makes it the next revision, and a page fetched earlier through `--url` and the same page given as a file are one resource. The request keeps the file's `input_sha256`, so a replay with other bytes is a binding mismatch. Not with `--url` (the identity of a URL capture is computed), not with `--site`; in a batch manifest each item has its own `canonical_url` and `tier` keys. The inbox does not read `request.canonical_url` yet and still refuses `tier: bookmark` envelopes (phase 1 D12) — both land with the producers.

## 16. Text mismatch audit — is the body of an old capture its page's text?

Captures made before the capture contracts have a `source.md` that nothing ever checked against a raw: no `capture:` block, no `completeness`. A capture of that era could publish text that is not the page's — a summary instead of the article, a converter's selection that kept a sidebar and lost a section — and the body's length does not tell. Where the archive kept the raw, the audit asks the question §2 asks, in reverse: does the text of the body occur in the text its raw converts to now?

```bash
mnemon audit text-mismatch                # current url revisions without a completeness record (bookmarks excluded)
mnemon audit text-mismatch --cited        # only those a collection, a wiki page or a synthesis note cites
mnemon audit text-mismatch --all-url      # every url revision with a raw: current or superseded, any completeness
mnemon audit text-mismatch --json         # the mnemon-text-mismatch-audit/1 document
```

**What it does.** For each revision it finds the raw — the archive member that `archive:` names, else `<revision>.<ext>` in the archive, else in the state dir's `raw/` — and converts it with the converter a re-capture would use, in a bounded subprocess that writes only into a private temp dir (a revision's sidecar `<revision>.report.json` lends its fetch report when it is on this machine; a cloud placeholder is not opened, and the row says `sidecar: unavailable`): an HTML raw through `capture-text.py` (§2, under `convert_timeout` or `--timeout`), a PDF through `pdftotext -layout`, a site bundle through `capture-site.py assemble`, a text raw as it is. Then every eligible line of the body must be found in that text, by the rule of §2 with the roles swapped: the body is reduced to its text first (frontmatter dropped; links to their text; images and the sanitizer's figure markers dropped; heading, list, quote and task markers removed; entities decoded outside code spans) — the raw's text goes through the same reduction, so an unchanged capture compares equal — the eligibility is §2's (six words, a heading of two, twenty characters of a script without spaces, the chrome list, not the title), and a line counts as found with its word boundaries — the word sequence in order, not only the letters.

| Class | Meaning |
|---|---|
| `match` | every eligible line of the body is in the raw's text |
| `mismatch` | some are not: the share of eligible lines not found, and up to three of them |
| `unprobed: no raw` | the archive and the state dir hold no raw for the revision (`archive: unarchivable`, a reference to a missing file, none at all) |
| `unprobed: no eligible lines` | the body has nothing the rule can require |
| `unprobed: converter unavailable` | no converter here (`pdftotext` missing, a raw of a kind nothing reads), or the conversion timed out or failed on its own |
| `unprobed: raw unreadable` | the raw cannot be read: permissions, bytes that are not text, or a cloud placeholder whose bytes are not on this machine — the audit never downloads one |

**How to read it.** The command reports **text mismatch candidates**: lines of the body that the raw's text does not hold, never why. A body that is not the page's text gives a high share; so can converter drift (today's converter keeps other text than the one that made the capture — `capture-text.py`'s content subtree drops navigation, footers, forms and comment sections), an old selection that kept what the subtree now drops, and lines the old capture wrote itself (a header with the URL, a note). A share of a few percent is usually that; a share near 1 with samples that read like a summary is worth opening. Each mismatch row also shows the body's and the raw's word counts and, for an HTML raw, its acquisition classification (§2): a raw that is `thin`, a `js-shell` or a `bot-wall` page missed the page itself, and its mismatch says so before any line is read. The door is a re-capture, `mnemon add --url <url> --recapture`: the new revision supersedes the old one, and a wiki page built on the old one becomes stale and is rebound through the research workflow ([research.md](research.md)) — the audit changes nothing itself.

**What it never does.** It writes nothing into the vault, the archive or the state dir, takes no lock and fetches nothing; a temp dir inside any of them is refused. It is not a check of `mnemon doctor --data`: the data doctor's 19 checks are a frozen interface, and a conversion per revision does not belong in a session-start hook. Exit 0 whenever the audit ran, whatever it found. The rule and the document are the capture layer's amendment A17 ([`specs/2026-10-15-capture-layer.md`](specs/2026-10-15-capture-layer.md) §18).

## 17. Texts and files — `--file-text`, a plain-text `--file`, the session

A text is captured **as its bytes**: no converter, no check, `fidelity: exact`, the text is its own raw (`raw_store: none`). Three doors lead there (capture contracts A14):

```bash
mnemon add --origin text --title "A note" < note.txt        # stdin; the bytes are kept as runs/<id>/attempt-1/capture.md
mnemon add --file-text note.txt --title "A note"            # a file; the file itself is the input locator
mnemon add --file note.txt --title "A note"                 # a plain-text --file takes the --file-text route
```

`--file-text <path>` captures the file's bytes exactly: origin `text`, `capture.method: file-text`, the resource keyed by the sha256 of the bytes, the path recorded as the receipt's `input_path` (a replay re-reads it and refuses changed bytes as `input-missing`). A `--file` whose origin is auto-detected takes the same route when it is **plain text**: the extension `.txt` or `.text` in any case, or no extension and `file` types it `text/plain`. Before this rule such a file went through pandoc as Markdown, and the published text was not the file (emphasis and list markers rewritten, CRLF and trailing spaces lost). The bytes are not normalized — CRLF, a BOM and trailing whitespace stay as given — and invalid UTF-8 fails as `invalid-utf8` (exit 1, nothing published). A text with nothing but whitespace (an empty file included) fails as `no-text` on every door — there is nothing to capture or extract. `--origin file --file notes.txt` keeps the file route on purpose (the raw retained, `pandoc:markdown`); any other file, `.md` included, is converted as before. `--canonical-url` works with every door (§15). A plain-text file captured before the rule is the same resource: a new `--file` of the same bytes answers `skipped-duplicate` with that revision, and `--recapture` makes the exact revision that supersedes it. A capture id recorded before the rule replays as it was recorded — an inbox or a feeder that repeats `--file <path> --capture-id <id>` is bound as the origin-file request it was.

**The session.** `extract.md` records the session a capture was made in (`capture_context.session`, also in the receipt and the prompt's capture context). It comes from `--session <name>`, else from the caller's `MNEMON_SESSION`, else it is empty; an explicit empty `--session ""` wins over the environment. Every `mnemon add` reads `MNEMON_SESSION` — the ones `mnemon ingest` runs too, in the environment it was started in — so a feeder started under another session's environment labels its captures with that session; start it with the variable unset when that is not meant. A replay and `--resume` keep the session the receipt recorded — a retry from another session never relabels the capture. `mnemon browser-lane youtube … --session <name>` passes it to the `add` it runs and prints it in every command it shows (capture contracts A13).

## 18. Images and screenshots

A source saved from a phone sometimes exists only as a screenshot. Two shapes recur. A *pointer*: the image shows a document's address (a full URL, an arXiv identifier, a DOI), and the wanted source is that document. *Content*: the image holds the text, and no other copy is at hand. The engine handles the content shape only. It never reads an address out of an image and never fetches one: the session that hands the image over reads the address and captures the document by its URL (the `/source-add` skill's door, below). The contract is capture contracts A15 ([§18](specs/2026-10-15-capture-contracts.md)), amended by A16 (§19); the mechanics are capture layer A20 ([§21](specs/2026-10-15-capture-layer.md)), amended by A21 (§22).

**The door — explicit only.** `mnemon add --origin image --file <image> [--ocr-languages <sequence>]`, with `--title`, `--author`, `--intent` and `--session` as for any capture, or an item `{"origin": "image", "file": "…", "ocr_languages": "rus+eng"}` of a `--manifest` batch. An image is never auto-detected: a PNG or JPEG given as `--file` without `--origin image` takes the `file` row and fails `unsupported`, and that message names `--origin image`. The inbox takes no image payload yet (an image envelope still ends `unsupported`). Refused with `--origin image`, exit 2 before any write (the dry run runs the same checks): no `--file`; `--file-text`, `--ref-path`, `--manifest`; `--url`, `--canonical-url`; `--site`, `--media-bundle`, `--render`, `--no-render`, `--no-external`, `--depth`; `--tier bookmark`. `--ocr-languages` with another origin, at the batch level, or outside its grammar is refused too. A batch item with `origin: image` and any of the keys `url`, `ref_path`, `content`, `canonical_url` or `tier` — by the key's presence, whatever its value — starts no child: the batch prints `ERROR: item <n>: origin image takes no <key>`, counts it failed with exit 2 and goes on.

**What leaves the machine.** An image capture sends the image to the model your `claude` uses — the account and provider that Claude Code is logged in to, the same that receives the text of every other capture for extraction. One invocation per attempt sends it, with a fixed transcription prompt, with no tools and no saved session. tesseract reads the same image on your machine. Do not capture as an image what must not leave the machine. The engine sends the image only after the envelope check has accepted it and the witness has read it; an image that fails either never leaves the machine through the engine. A dry run sends nothing. This is a statement about the engine's own data flow: a caller may show the image to a model before it calls the engine — the `/source-add` skill does, because its session looks at the image — and the engine neither knows nor prevents that. An image that the session reads only as a pointer is never captured, and the engine sends nothing of it.

**Formats, orientation and limits.** The bytes' signature decides the format, never the file name: PNG (`89 50 4E 47 0D 0A 1A 0A`) and JPEG (`FF D8 FF`). JPEG bytes named `.png` are a JPEG, kept as `<revision>.jpg`. Everything else fails the envelope check as `unsupported` with `RESULT:acquisition=wrong-format`: GIF, WebP, TIFF, BMP, HEIF/HEIC, AVIF, a PDF, an animated PNG, unknown bytes. A container cut short is `truncated`; an inconsistent one (a header, a frame, the EXIF block) is `corrupt`. **Upright only**: an EXIF orientation other than 1 is `unsupported`/`rotated` — phone screenshots are upright, and tesseract does not apply the tag. The envelope check decodes no pixel: a file whose compressed data is broken passes it, and the witness refuses it (`unsupported`/`corrupt`) before the image is sent anywhere. Three limits, each refused as `too-large`: `image_max_bytes` (7 000 000 by default; the provider's documented cap is 10 MB of base64 per image, and an operator whose `claude` uses Amazon Bedrock, documented at 5 MB of base64, lowers the key), `image_max_pixels` (50 000 000) and `image_max_edge` (8 000 px, the provider's documented maximum dimension; measured on synthetic columns of text, every word was read at 8 400 px, and from 10 500 px the model no longer read every block). **The engine never shrinks, rotates or recompresses an image**: the reader and the witness get the raw bytes, and an image over a limit is refused. The edge cap decides which inputs the engine accepts; it does not promise a complete reading under it — the comparison stands against that.

**Who reads and who witnesses.** The **reader** is a small vision model (`image_reader_model`, default `haiku`), called once per attempt through `claude -p` under the extractor's fence: no tool but `StructuredOutput`, no MCP server, no saved session, the raw bytes and a fixed transcription prompt, nothing of the vault, an effort level pinned in the call (`image_reader_effort`, default `high`) and a budget cap (`image_reader_max_usd`). Its reading, normalized, is the capture-text: the body of `source.md`, `capture.fidelity: recognized`. A reading is not repeatable — two attempts may give two texts — and a published revision holds exactly one reading. The **witness** is tesseract on this machine; it opens no socket. Its text is compared with the reading and, as a whole, never published: only its words and numbers that found no partner in the reading are kept, in the capture's report. It is repeatable on one installation: the same image under the same tesseract, language models and options gives the same text. The witness is mandatory and runs first: an attempt checks the envelope, probes the witness, runs it, then calls the reader, then compares. Without tesseract, or without a language model the sequence names, no image capture runs — the attempt ends `environment` (exit 3) with the image kept, and costs no model call. Every published reading was compared.

**The witness's languages.** The reader needs no language hint; the witness does. `--ocr-languages <sequence>` sets it for one capture, else the instance's `ocr_languages` (default `eng`): tesseract codes joined by `+`, the main language first — `eng`, `rus+eng`, `ukr+eng`, `chi_sim` — one to eight codes, none twice. The order matters and the sequence is bound in the request (`rus+eng` is not `eng+rus`); the engine never sorts or guesses it, and a missing language model is exit 3, never a fallback to another sequence. **A wrong sequence makes the engine refuse a correct reading**: the witness then reads junk (measured: a Russian post read as `eng` had a character error rate of 87.6 %), junk is absent from the reading, and the comparison refuses. When a reading is refused, check the sequence first. Another sequence is a new capture of the image, with the original file (no `--recapture`: nothing was published); a replay by `--capture-id` witnesses with the bound sequence.

**The comparison, in plain words.** Both texts are cut into words (runs of three letters or more, lowercased, with `l` and `I` read as one letter — the two readers split on that stroke) and numbers (digits with inner dots and commas: `12.3` is not `123`), and each word of one text answers for one equal word of the other. A word broken at a line end with a hyphen is joined when the other text holds it whole. Three refusals, each with the image kept and the capture replayable:

- **No text** — the reading has no character but whitespace: `no-text`.
- **A gross loss** — more than 20 of the witness's words (`image_miss_allowance`) are absent from the reading **and** fewer than 90 % (`image_min_witness_share`) of them are found: `reading-mismatch`, `RESULT:acquisition=words-missing`. Both conditions must hold, so a quote card is not refused over three junk words.
- **No confirmation** — the reading has words and the witness confirms none of them: `reading-mismatch`, `no-confirmation`. This rule has not met a real image yet; by its terms it also refuses a right reading of an image in which the witness reads no word.

Everything else is published with its counts: the share of the witness's words found, the witness's words missing, the witness's numbers that the text does not hold, and the reading's words and numbers that the witness does not confirm. What the floor catches: a reading that dropped a block or stopped early — seen once on a real page (72.4 % found, 105 words missing). What it does not catch: the loss of a sentence or of a line, the order of the blocks, the meaning. Nor a lost number: the floor counts the witness's missing words only. **A number that the witness read and the text does not hold is counted apart, and never refused** (`capture.witness_missing_numbers`, since rule `mnemon-read-compare/2`): numbers are matched in both directions, and the unconfirmed numbers are the other direction. The count is a place to look, not a verdict. A rough count on four real screenshots found eleven such numbers; by eye three were a real loss — a time range in an overlay — and eight were digits that tesseract read off icons and counters. The rule's own counts on new readings of the same four: eleven again — three lost, the phone's status bar on one screenshot; seven tesseract's own; one that cannot be told. A missing number names no place: numbers are matched by their spelling as written, with multiplicity and without positions, so a check needs the image and the published text together. **An addition is counted, never refused**: in one of nine readings of a real page the model wrote a paragraph twice, 69 words stood unconfirmed, and the verdict was to publish. **An unconfirmed word is not a wrong word**: on four real screenshots read once each, 60 words and numbers were unconfirmed — 43 were text the witness cannot see (on a dark ground, in a chart, rotated, small), 6 were words completed past the screen edge or under an overlay, 11 were words the two readers had split differently (the hyphen repair now joins ten of those), and none was a substitution. A number misread by the model lands among the unconfirmed numbers, beside right numbers the witness did not see either. The refusals are heuristics over word counts: their rates of false refusal and false acceptance are not measured, and the floor rests on readings of four real screenshots. The two floor keys are limits, not bound in the request: move them and replay.

**Outcomes and what a replay does.** `RESULT:status` is the terminal state; the image's own classification travels on `RESULT:acquisition=`. `reading-mismatch` is the one new class (`retryable: false`).

| the reading agreed, extraction failed | the extractor's (`captured`) | 4 | kept | per class |

A replay is `mnemon add --capture-id <RESULT:capture_id>` (or `--resume <capture id>`), and it does one of two things. Before publication it is a whole new attempt; after publication it reads nothing again. **Before the image is kept** (`fence-unprobed` at the start of a capture, `too-large` over the bytes), a replay reads the original file again and verifies it against the hash the request bound — after `mnemon fence-probe`, or after raising `image_max_bytes`; `input-missing` answers `input-missing` again. **After the image is kept and before publication**, every replay is a whole new attempt from the kept image: a new run of the witness, a new call of the reader, a new comparison, and the original file is not needed. Such a replay checks the reader's fence record again, so it too can end `fence-unprobed` (after a Claude Code upgrade, say): run `mnemon fence-probe` and replay the id once more — the image stays kept. A kept image that is missing or changed ends every replay `evidence-mismatch`: recorded evidence is never acquired again, and the operator repairs it. After `environment` it is the retry once the tool, the language model or the login is in place. After `reading-mismatch` it helps when the reading was at fault (the next one may differ) or once the floor was moved. After the other permanent failures it helps once the operator changed something — the witness, a language model, a cap, `image_timeout`, `image_reader_max_usd`. A crash during an attempt is answered the same way: the interrupted attempt's reading, if it was made and not recorded, is lost with its cost. When a new attempt's reading differs from the last recorded one, the gateway prints `NOTE: this attempt's reading differs from the previous attempt's`. **After publication** no replay and no `--resume` reads again — no witness, no reader: `--resume` finishes the extraction. A new reading of a published image is a new revision: `--recapture`. The engine never chooses among readings and never merges two.

**The notes.** For every published image revision — a fresh capture, a replay, a resume, a duplicate — the gateway prints on stderr `NOTE: the local recognizer does not confirm <n> word(s) and <m> number(s) of the text` when either count is above zero, then `NOTE: unconfirmed numbers: <list>`, with at most twenty, when the number count is above zero. Each number is listed as the reading spells it, digits of any script included, without control characters and whitespace, so the line stays one line. Without these lines both counts are zero. Then, when the witness read numbers that the text does not hold: `NOTE: the local recognizer read <k> number(s) that the text does not hold` and `NOTE: missing numbers: <list>`, with at most twenty, each as the witness's text spells it, under the same character rule. Without these two lines that count is zero, or it was not counted (a revision compared by rule `mnemon-read-compare/1` has no `capture.witness_missing_numbers`), or an engine of an earlier release printed the notes: `capture.witness_missing_numbers` in the frontmatter tells which. Last, `NOTE: the reading's report: <path>` names the report file of the reading (below) when the engine has it in place, whatever the counts are. Without that line the engine named no file; it is not proof that no report exists (a sidecar whose publication failed is repaired on the next replay; an instance without `archive_dir` has none). A replay before publication is a new attempt, and its lines come from its new report. A replay or a resume of a published revision, and a duplicate, read nothing again, so their lines come from the stored report of the one reading; without a readable report each count line that is printed says that the list is unavailable, and no list line follows it. After a `reading-mismatch`, the engine's message is a sentence of numbers — the share, the missing count, the floor, the witness's languages and its mean confidence — and holds no word of either text.

**The `capture:` block of an image.** No URL key is written (`url:`, `canonical_url:`, `final_url:` and the rest): a later `--url` capture of the document a screenshot shows is never answered by the screenshot, and neither supersedes the other. No orientation is written: a published image is upright by construction.

```yaml
origin: image
source_type: article                  # the default for an image; --source-type overrides
content_format: text
origin_path: "…"                      # the --file path as given: context, not evidence (the raw is the evidence)
capture:
  method: "read:claude-haiku-5-5"     # read:<the model id the call reported>
  fidelity: recognized                # a machine reader turned pixels into the text
  raw_store: archive
  raw_kind: image
  raw_sha256: "…"                     # = the request's input_sha256
  raw_bytes: 1306624
  text_sha256: "…"
  text_bytes: 1468
  converter: image-reader
  completeness: unknown               # the witness is a second reader, not a reference
  image_format: png                   # png | jpeg, from the signature
  image_pixels: "1320x2868"
  reader_adapter: "image-reader/1"    # fixes the prompt, the schema and the argv
  reader_claude_code: "2.1.328"
  witness_backend: tesseract
  witness_version: "5.5.4"
  witness_adapter: "ocr-tesseract/1"
  witness_languages: "eng"
  witness_execution: "…"              # the witness's execution key
  compare_rule: "mnemon-read-compare/2"
  witness_share: 95.9                 # percent of the witness's words found in the text; absent when it has no word
  witness_missing_words: 8
  witness_missing_numbers: 4          # numbers the witness read that the text does not hold; absent under rule /1 (not counted)
  compared_words: 187                 # the text's words by the comparison's rule
  unconfirmed_words: 1                # words of the text the witness does not confirm
  unconfirmed_numbers: 2              # numbers of the text the witness does not confirm
  engine: "…"
```

**The report.** The lists, the witness's confidence, the verdict and the reader's cost are in the report, not the frontmatter: the receipt keeps it (`capture_report.text`), and the archive sidecar `<revision>.report.json` freezes the report of the published reading. The engine prints the sidecar's path (`NOTE: the reading's report: <path>`); the image report is the file's member `text`. A report of the schema `mnemon-capture-image/2` holds `comparison.verdict`, `reader.cost_usd` with the token counts, and two list objects of at most 200 words and 200 numbers each, with `truncated` when one was cut: `comparison.unconfirmed` (the reading's words and numbers that the witness does not confirm) and `comparison.missing_lists` (the witness's words and numbers that the reading lacks, as the witness's text spells them). In that schema the word `missing` has one meaning — what the witness read and the reading lacks: `comparison.missing_words`, `comparison.missing_numbers`, `comparison.missing_lists` — and what the witness's installation lacks is `witness.absent`. A report written before that schema is `mnemon-capture-image/1`: it holds the count of missing words as `comparison.missing`, no list of them and no count of the witness's numbers. It stays as it is: no stored report is rewritten, and a replay or a duplicate of such a revision prints its notes from it. **What carries text of the image**: the two list objects, the two notes that list numbers, and `RESULT:title=` (the extract's title is written from the image's text). Every other `RESULT:` line and note of an image capture holds identifiers, kinds and counts; a feeder that must pass on no text of an image treats those four as content. The receipt's `read_history` keeps one entry per attempt that ran the worker — its outcome, the hash of its reading, its cost and token counts — so what the readings cost stays on record after the attempt dirs are cleaned. The local `tessdata_dir` stays in the receipt and the sidecar and never reaches the frontmatter.

**Configuration** — instance keys, read like §12's (`mnemon config get`, `mnemon config dump`, `mnemon.yaml.template`). The sequence is bound in the request; the other nine are limits read at run time, and each attempt's report records the values it ran under.

| Key | Default | Meaning |
|---|---|---|
| `ocr_languages` | `eng` | the witness's languages: tesseract codes joined by `+`, the main language first, one to eight, none twice |
| `image_reader_model` | `haiku` | the reader's model, as `--model` takes it; the report records the model id the call reported |
| `image_reader_effort` | `high` | the reader's effort level (`low`, `medium`, `high`, `xhigh`, `max`), pinned in the call; `high` is a provisional default from three readings of one hard page |
| `image_reader_max_usd` | `0.05` | the reader's `--max-budget-usd` (the costliest call measured was $0.0041); checked between turns, so the deadline bounds one long call |
| `image_timeout` | `120` | the deadline of one image: the envelope check, the witness, the reader's call and the comparison (measured: at most 30.3 s for the reader, 1.2 s for the witness) |
| `image_max_bytes` | `7000000` | the input's size cap, checked before the copy and again by the worker |
| `image_max_pixels` | `50000000` | the `width × height` cap |
| `image_max_edge` | `8000` | the cap on the longer side, in pixels |
| `image_min_witness_share` | `90` | the floor: the percentage of the witness's words that must stand in the reading (0–100) |
| `image_miss_allowance` | `20` | the floor: the number of the witness's words that may be missing whatever the share |

The ranges: `image_timeout`, `image_reader_max_usd`, `image_max_bytes`, `image_max_pixels` and `image_max_edge` must be greater than 0; `image_min_witness_share` lies in 0–100; `image_miss_allowance` may be 0; none of the numeric keys takes a negative value. A value outside its range is refused when the config loads: the command prints one line, for example `ERROR: image_timeout must be greater than 0, got '0' (<config file>)`, and exits 2 before any capture starts.

**Install.** On macOS, `brew install tesseract` (it brings the English language model, `eng`). Other languages: `brew install tesseract-lang` for all of them, or one `<code>.traineddata` file put into the directory that `tesseract --list-langs` names (or that `TESSDATA_PREFIX` names, when it is set). On Ubuntu the packages `tesseract-ocr` and `tesseract-ocr-<code>` are expected to work and are not shown yet: the live gate has not run there. Then run `mnemon fence-probe`: its sixth probe, `image-reader` (a real `claude` run on a committed synthetic image, about one cent), checks the reader's fence for the installed Claude Code version, and gates images alone. A version whose image probe failed keeps extracting and captures no image (`fence-unprobed`, exit 3: at the start of a capture, before the image is kept, or on a replay of an image already kept); a record written before the probe existed has no image entry, and `mnemon fence-probe` adds it. Run it again after every Claude Code upgrade.

**Doctor and dry run.** `mnemon doctor`'s `capture-deps` line has two image parts, both observational. `ocr tesseract 5.5.4 (models: eng, osd, rus)` names the witness and the installed language models; it warns with `ocr missing — image captures exit 3: brew install tesseract`, on a version older than 4 or unreadable, on a missing model of the instance's sequence (`ocr_languages rus+eng: rus missing`), and on a probe over its time or output limit. A model counted present is a regular file; whether it loads, only a run shows. `image-reader haiku (fence probe: pass)` says the fence record of the installed Claude Code holds the image probe; else it warns `image-reader: no fence probe for images on Claude Code <version> — image captures exit 3: mnemon fence-probe`, and `mnemon doctor fence` names the same. `mnemon add --origin image --file <image> --dry-run` prints the raw's extension by signature, the bound sequence, the limits and the floor, the witness's probe (tesseract found, its version, its model directory, each language model present as a file or missing) and whether the fence probe record holds the image entry. It cannot show that a language model loads or that `claude` is logged in: only a run shows those. It makes no reading, calls no model, writes nothing, and **exits 0 also when the run would exit 3** — it prints that exit and its reason.

**The `/source-add` skill.** A Claude Code session handed an image looks at it, captures at once by URL each document the image plainly points to (its own page, or a card or preview that presents it with its address), and captures the image itself only when it holds text of its own, when the document has no usable address, or when the document's capture failed. A reference inside a post's running text is a mention: it is named in the report and not captured. The session chooses the witness's languages, reports the comparison in one of three forms (published with a share, published without one, not published), and never passes its own reading of the image as `--origin text`. Since plugin 0.4.5 it lists the witness's numbers that the text does not hold and checks each of them against the image and the published text — lost, tesseract's own, or cannot tell — as its own look, never as a gate; it passes a caption as `--title` only when the user wrote or confirmed it; it chooses the instance by the user's word in the request, else a standing rule of the project, else its own, and names the instance in its report when it is another. The text is the skill's ([`plugins/mnemon/skills/source-add/SKILL.md`](../plugins/mnemon/skills/source-add/SKILL.md)).

**Later work** (not in version 1): a schema for what an image shows beyond its text; auto-detection of an image together with the inbox's `image` origin, with the first producer that sends images from a phone (that amendment decides whether an unattended pass may send an image to a model); an operator's override for one refused reading; a witness that reads a framed block inside a page; the witness's languages chosen from the reading's script; a tall capture read in tiles; a second reading compared with the first; a check of additions tighter than a count; HEIC, WebP, GIF, TIFF, BMP and animated images; rotated images; an image by URL; a public reader or witness interface; the macOS Vision recognizer as a witness; several images as one source.
